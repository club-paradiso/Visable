## F2 (R2): the "verified" flag no longer authorizes every article number

- **Defect.** `guard_answer_citations` returned `allowed_verified` for every article number the model wrote whenever `law_grounding_verified` was true, but that flag is also set by a law-title list hit. R1 hid this; F1 would have switched it on.
- **Evidence.** Audit R2; `law_citation_guard.py` (HEAD) lines 126-128. Re-shown on HEAD: `test_f2_verified_flag_alone_no_longer_authorizes_article_numbers` → `'allowed_verified' != 'notice_prepended'`. A reference the text does not name (a bare `시행령`, the tail of a multi-word `…에 관한 법률`, a sentence boundary) binds nothing, so the scanner fails closed. Tokens that are not bound fall through to the existing local-evidence check and then the existing notice. Return keys and action names are unchanged (`none`, `allowed_verified`, `allowed_local_evidence`, `notice_prepended`). `article_evidence_from_law_pack(pack)` (new) extracts those rows from a pack for a future caller.
- **Wiring.** `/api/ask` calls the guard from `paradiso_backend._apply_law_citation_guard` (paradiso_backend.py:1016-1036), which is off limits. It passes no `article_evidence`, so on `/api/ask` the flag now never allows anything by itself: every article token must appear in the evidence texts that function already collects (law_sources `law_name/article/title/summary`, the evidence summary, manual sources, structured block). After F1 that set includes a fetched article's label and text, and title-only rows contain no article tokens.
- **Tests.** `F2CitationGuardTests` (synthetic, fictional names `가상체류관리법`, `가상노동법`, no law ids): flag alone; 11 binding cases (same law, `같은 법`, other law, 시행령 of the same law, mixed with 시행규칙, 별표, bare article, bare 시행령, multi-word 법률 title, `같은 법 시행령`, earlier sentence); mixed fetched + local evidence → `allowed_local_evidence`; article evidence without the flag → notice; return shape. - **Residual risk.** Multi-word law names (`재외동포의 출입국과 법적 지위에 관한 법률`) cannot be bound by the scanner, so a fetched article of such a law is still only allowed through the local-evidence path (fail closed). The notice text says the real-time lookup could not be confirmed, which is imprecise when the law was found but the article was not; it was left unchanged (Korean UX copy, mirrored in the owner's `ai.html`).

## F8 (R7): the OC is only sent to https law.go.kr

- **Defect.** The Python `LAW_API_BASE_URL` override sent the OC to any host (the JS client checks the host). An older strategy doc suggests pointing it at a third-party host (docs/EXTERNAL_SKILLS_AND_LEGAL_GROUNDING_STRATEGY.md:74).
- **Evidence.** Audit R7 / §(f). HEAD: `search_laws` with `LAW_API_BASE_URL=https://korean-law-mcp.fly.dev` sent three OC-bearing URLs to that host (query search plus two cloud-fallback pages); `http://www.law.go.kr`, `https://www.law.go.kr.attacker.example`, userinfo, port 8443 and `ftp://` overrides were all used as given.
- **Change.** `law_tools._trusted_base_url` accepts only `https://www.law.go.kr` or `https://law.go.kr` (no userinfo, port 443 or none, no query or fragment). `_api_host` falls back to the default `https://www.law.go.kr` for anything else and logs the code `LAW_API_BASE_URL_IGNORED` once per process without the configured value. `law_api_base_url_warning` exposes the same code, and `law_grounding_preflight` adds it to `warnings`.
- **Scheme swap: why it exists, and the decision.** `git log -S _transport_with_scheme_fallback` finds one commit, `42f0820` (#432, 2026-06-16), "Make law.go.kr transport scheme-resilient (https<->http fallback)". Its message says the earlier unconditional http→https default fixed cloud egress but risked breaking a deploy where only http reaches law.go.kr, so on a connection-level failure the transport retries once with the other scheme. It was added during a production outage of law grounding. The egress premise ("Railway blocks port 80", the `CONNECT tunnel failed (000)` symptom) is not established: docs/integrations/LAW_OPEN_API_RUNTIME_PROBE_2026_06_14.md and LAW_GROUNDING_LIVE_SMOKE_RESULTS.md:37 record that symptom from the agent sandbox's proxy against the Railway URL, not from Railway egress. Nothing in the repository or the live captures records which scheme production actually uses: the law modules had no logging, and L4 (2026-10-19) shows only that production reaches law.go.kr. So the history does **not** show that production is independent of the http retry, and the rule for this mission is to leave it unchanged. Behaviour is unchanged. Two things changed around it: (1) with the host allowlist, the plaintext retry can only target `www.law.go.kr` / `law.go.kr`; (2) the retry now logs `LAW_API_PLAINTEXT_RETRY_REACHED` or `LAW_API_PLAINTEXT_RETRY_FAILED` once per process, with no URL and no OC, so the owner can see whether a deploy depends on it.
  **Risk, for the owner:** whenever an https connection to law.go.kr fails at the connection level, the OC is resent over plain HTTP, and `legal_evidence` retries make that up to 3 plaintext sends per request (audit verifier omission 3). **Recommended owner step:** after deploying, search the Railway logs for `LAW_API_PLAINTEXT_RETRY_REACHED`. If it never appears over a representative period, gate the http retry behind an explicit opt-in env flag and update `test_law_tools.py:105-175`, which asserts the current fallback.
- **Tests.** `F8HostTrustTests`: six untrusted overrides fall back to the default host with the warning; `https://www.law.go.kr` and `https://law.go.kr/` are kept with no warning; no transport call reaches an untrusted host; the scheme fallback still goes https→http and stays on www.law.go.kr even when an untrusted override is configured; the plaintext retry log is emitted once and contains neither the dummy OC nor the request path; the base-URL warning appears in the log and in preflight without the configured value or the OC.
- **HEAD → fix.** `False is not true : https://korean-law-mcp.fly.dev/DRF/lawSearch.do?OC=genesis-dummy-oc&…` (and one per untrusted override); `AttributeError: … 'law_api_base_url_warning'` / `'_WARNINGS_LOGGED'` for the new API → all pass.
- **Residual risk.** If Railway sets `LAW_API_BASE_URL` to a proxy, the next deploy stops using it (see the next section). `korean_law_client.KoreanLawClient` (legacy, imported only by tests) still sends a Bearer credential to any configured host; it is outside this mission's files.

## F9 (SEC-05b, audit D6): failure is not absence in the DRF parser

- **Defect.** On `fc896c2`, `_parse_payload` returned `law_api_no_results` for an empty HTTP-200 body (law_tools.py:584), and `parse_law_search_response` returned `law_api_no_results` for every well-formed body in which the walker found no row, whatever its shape (607-612). `_official_error_info` (493-536) read `msg`/`message` for a few error words and never read `result`, so the envelope law.go.kr returns with HTTP 200 to a request without OC (`{"result": …, "msg": …}`, no `resultCode`; official-api.md V-E, OBSERVED 2026-10-19) also read as "no results". `legal_evidence.LawOpenDataClient._normalize_response` did the same for precedent lists (legal_evidence.py:959-960). For a cited law, "no results" becomes `failed_verification` + `CITED_LAW_NOT_FOUND`: a credential problem or an upstream format change told the user the law does not exist (spec 07 §2 invariant 1).
- **Evidence.** 15-security §3.6 and §5 (probe: missing-OC envelope → `law_api_no_results`; empty body → `law_api_no_results`; XML 860-988 deep, well-formed, no rows → `failed_verification` + `CITED_LAW_NOT_FOUND`). Re-shown on both baselines: empty body `'law_api_no_results' != 'law_api_bad_response'`; missing-OC envelope `'law_api_no_results' != 'law_api_official_error'`; `{"LawSearch": {}}` and six other bodies without an empty answer `'law_api_no_results' != 'law_api_parse_error'`; the cited-law search with an empty body, the missing-OC envelope or a body without a result list `'failed_verification' != 'error'`; `legal_evidence` `'no_results' != 'unavailable'`.
- **Change.**
  - `_parse_payload`: an empty or whitespace body is `law_api_bad_response` / `empty`. HTML stays `law_api_bad_response`, and anything neither JSON nor XML stays `law_api_bad_response` / `unsupported_text`.
  - `_official_error_info` looks only near the root (F11) and recognizes, besides the old code and message rules, `resultMsg` as a message key, and a scalar `result` with a non-success value when a message key sits beside it or the value itself contains a failure word.
